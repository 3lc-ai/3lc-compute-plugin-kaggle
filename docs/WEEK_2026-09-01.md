answering it**, and the README's "Scope" paragraph was right not to guess.

## 3. Thursday 2026-09-03

### 3.1 v1.2.10 — the project-root defects

**How it was found: Gudbrand set a non-default `project-root-url` and ran the
real path.** His symptom (`0cbc434`): Import created tables correctly, Train
and Predict autofilled paths under the *default* root and gated them red, and a
hand-corrected path went green but did not survive a reload. Two independent
defects, **both invisible on a default root**.

1. `importer._project_root_url` called
   `ConfigStore.instance().get(tlc_options.ROOT_URL)` — a **string**-keyed API
   handed an `Option` **object**. The lookup missed, returned `None` with no
   raise and no warning, and a truthiness fallback substituted
   `_get_default_root_url()`. Every derived table URL was built under the
   DEFAULT project root, **on every 3.x host, since v1.2.0**.
2. `config_store.url_project` (and its `ui.html` mirror `kgUrlSeg`) required a
   literal `/projects/` path segment. A root like `D:/3lc-data` has none, so
   `classify_override` answered `drop` and a corrected or hand-picked revision
   URL was never persisted — the reason the manual workaround died on reload.

Why Import looked fine throughout: creation passes `project_name=`/
`dataset_name=` and lets tlc resolve the root, so tables landed in the right
place while every URL derived *for another tab* pointed at the wrong one.

Fix: read `tlc.config.project_root_url`, the public accessor. Measured while
fixing, and the reason not to inline back to a keyed store read: **`ConfigStore.get`
returns values UNEXPANDED** — `~/3lc-data` and `${VAR}` come back literal, while
`tlc.config` expands them (verified on tlc 3.1.0.28 and 3.3.0). `tlcconfig` is
no longer imported anywhere in the plugin. Table URLs now parse by position in
the layout tail.

PRETAG_1.2.10 states its epistemic status plainly: the root cause was
established **by measurement, not inference**, and the symptom was reproduced
end to end in the backend on a genuinely non-default root — but **not** through
the browser. Verification highlights:

- The lookup misses silently on **all three** venvs: tlc 3.1.0.28 (dev), 3.1.0
  (`3lc-hub-next`), 3.3.0 (`3lc-hub-ga`) — "so this never worked on any 3.x host".
- End-to-end backend reproduction under a **bare** root
  (`<scratch>/gudbrand-root`, no `/projects/` anywhere): `_project_root_url()`
  → the configured root; all three splits `exists=True`; `classify_override` →
  **`keep`** for a `round2` pick, i.e. the reporter's workaround becomes durable.
- **Control run on the default root, same code, env var unset: unchanged.**
- **`pytest -q`: 157 passed** (86 before). **The new tests fail on the pre-fix
  source: 39 failed, 16 passed.**
- The two mirrors agree in **behaviour, not just text**: `kgUrlSeg` was
  extracted from `ui.html` and run under node v24.16.0 against the Python
  helpers on eight inputs — **all eight agree**, `None`/`null` included. Not
  added as a test: node is not a dev dependency.

**Why this class survived nine releases:** every fixture had been
default-shaped. The suite gained a project-root dimension — three root shapes,
default / relocated / bare.

### 3.2 v1.2.11 — the kit v2 rebuild

BSD-3 clause 2 needs the copyright notice inside the distributed kit. A CDN
version prefix is **immutable once staged**, so the notice cannot be added to
`v1` in place — it ships as a new prefix, and the constant that resolves the
prefix is plugin code. Hence a code release. Kit content:
`competition_exdark@78b3bf7`; plugin side: `16795c5`.

**The ordering that cannot be inverted:** `starter_kit_prefix()` resolves at
download time with **no fallback**, and `fetch_manifest` fails the job on a 404.
Tagging ahead of the dev → prod sync would hard-fail every tester on the Import
tab — the exact surface the release exists to improve. So: stage → sync →
verify live → **then** tag. PRETAG_1.2.11 records the prefix confirmed live
before the tag: manifest 2,848,920 B, sha256 `77F3A87E…` matching the committed
anchor, `Accept-Ranges: bytes`, ranged GET → **206**.

Build results, all measured:

- `check_kit_parity.py --dir` → **PARITY, matched 14005**, zero mismatches.
- **10 shards, all ten names identical to v1; the 9 image shards byte-identical**
  — checked at two independent layers (`archives[]` agreement, and a
  `sha256sum` diff of the on-disk zips that trusts neither manifest). Only
  `part-09-root-labels.zip` changed: 1,496,845 → 1,498,578 B.
- **Why that is structural, not luck:** `_plan_shards` iterates `sorted(groups)`
  and re-initialises `size = 0` *inside* the loop, so no size carries across
  groups; `root-labels` is 862,451 B against a 73,400,320 B budget (1.2 %), so
  it stays one shard at index 9. Holds for any root-file addition under ~72 MB.
- The v1 manifest shows **exactly** the intended delta: `size_mismatch: 2`,
  **`sha_mismatch: 0`**, `missing: 0`, `extra: 1`. Zero sha mismatches matters —
  `check()`'s `elif` chain reports size *instead of* sha, so a sha line would
  mean a file changed content at identical length. Nothing did.
- The license reaches the participant: extracted from
  `v2/part-09-root-labels.zip`, **1,502 bytes, sha256 `51340966…`**,
  byte-identical to `competition_exdark/LICENSE-ExDark.txt`.
- **The shipped bytes are the reviewed bytes.** Built to `cdn/_staging/v2`,
  verified, landed by same-volume `mv`. Never rebuilt in place: `created_utc`
  defaults to `now`, so a second run would change `manifest.json` while the
  shards stayed identical — the exact mixed manifest/data set the immutability
  rule exists to prevent.

**A bug found by running the suite after the bump:** `test_downloader.py`
spelled `"v1"` in ten assertions while the destination is
`dest / constants.STARTER_KIT_VERSION` — **the bump broke 9 tests**. Fixed by
*deriving*, not re-pinning, and proven version-agnostic by running the file
green against a temporary `"v3"` (15 passed) before restoring `"v2"`.

Kit content shipped: README retitled to "Low-light object detection - starter
kit" (clause-3 audit F5 — the old title led with the dataset's name to identify
our own deliverable); `## License / data use` rewritten with BSD-3 attribution,
the Loh & Chan *CVIU* 178 (2019) citation, the commercial-contact request framed
as **their** request, and CC BY 4.0 scoped off ExDark's images; the wrong

(`nvidia-smi`, never `nvcc`).

The `package_build/starter_kit/` copies were **regenerated from
`starter_kit/`** rather than edited, which closed two accumulated drifts: that

### 3.3 v1.2.12 — the divergent-source release

**How it was found: a deliberate class hunt, not a report.** Two shipped bugs
in two days shared one shape — a value derived correctly at one site while a
second site read a different, stale source, with nothing comparing them
(v1.2.10's project root; the kit version). `27f11b5` audited `src/` and
`ui.html` for that class.

**F1 — kit version, armed by v1.2.11's own bump.** Three sources could answer
"which kit is this": `constants.STARTER_KIT_VERSION` (write path), the job
record's `facts.kit_version` (read path), and the CDN manifest's own
`kit_version` (surfaced in a check-detail line and compared to nothing).
`16795c5` moved the first and not the second. Consequence: **a v1 holder was
told "downloaded 2 days ago" forever and no surface named a newer kit.**

That is why it was a release and not a batch (CLAUDE.md §B — fixes are
invisible to catalog installs until tagged): the symptom is *silence*, so no
tester would ever report it.

Fix: `download_state` returns a third state, **`superseded`**, kept distinct
from `stale` (= gone from disk) because one state string over two conditions is
the very class being closed. `verify_now` accepts superseded and stops falling
back to the current constant when a record names no version — that fallback was
the bug in miniature, looking under a directory the record never wrote and
reporting the manifest missing while a good kit sat beside it. `fetch_manifest`
now refuses a manifest whose `kit_version` disagrees with the constant.

**F10 — the Verify ratio could not go non-green.** The line took its denominator
from `v.matched` — the same number on both sides of the ratio — so it read "N of
N files match" on **any** kit. It now uses the published `file_count`, which the
server had always sent and the fragment had always discarded. Proven at DOM
level, not by reading: driven against `{ok: true, file_count: 14005, matched:
14002}` it renders "**14,002 of 14,005**"; the same payload before the fix
rendered "14,002 of 14,002" — a perfect ratio on a kit missing three files.

Verification discipline worth recording: **the new tests were observed failing
against the pre-fix downloader** (4 of 5; the 5th is a regression guard,
correctly green both sides) — "a test that passes before the fix is not testing
the fix". Every packaging assertion was **mutation-checked**, each firing alone.

**The honest limit, recorded deliberately in the PRETAG and in ui-notes §17:**
downloading v2 does **not** correct a v1 holder. `parse_dataset_yaml` resolves
`path: .` against the yaml's own directory, so the new kit lands in a new
directory while already-imported tables keep resolving into the old tree; and
because those tables still exist, `verified_import_state` keeps passing and the
Import tab stays in its revisit view. **They keep training against v1, wrong
README and all.** What v1.2.12 buys is that they are *told*, accurately, instead
of being told nothing. The in-place top-up is the fix that actually reaches an
existing holder; it leads the v1.2.13 register.
