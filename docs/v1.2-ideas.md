## Parked from the v1.2.6 release (2026-08-14) — v1.2.7 candidates

- **Fragment-version echo + 409** — the fragment sends its build version
  with every `/config` write; the worker answers 409 on mismatch; the
  fragment surfaces a reload banner. Justification: the 2026-08-14
  stale-fragment finding — B3's 400 rejection is correct but invisible
  mid-flow, because the v1.2.5 fragment's save path swallows every save
  error (`.catch`, best-effort); a user sees nothing until values revert
  on reload. The tester note's required hard-refresh is the workaround;
  this handshake is the fix. (This was the recorded alternative when B3
  was chosen over accept-and-strip in Phase 3; first on-disk record.)
- **Setup script derives the plugin version from the catalog** — fetch the
  gist `catalog.json` (the same URL the tester pastes) and build the
  managed-venv path from its manifest version, so the env var always
  pre-states exactly what the shop is about to install. Parked, not
  ridden with the v1.2.6 pin fix: it makes the setup script
  network-dependent at the exact moment a fresh tester is most likely to
  be behind a proxy or offline — a new failure mode introduced at the
  finish line in the one script whose job is unsticking people. A
  hardcoded fallback would re-create the defect it fixes, so the
  no-fallback design needs its own testing pass. Class finding recorded
  in v1.1-ideas.md (LAUNCH-VERIFY, version-drift CI check).
- **P1 — local mAP@0.5 stopped populating (host-side scoring)** — last
  populated run `smoke_020_port` (~2026-07-31); every run since shows
  "–" in Status. Host mode confirmed ON at observation time (the
  "Weights file" affordance renders), so this is NOT participant
  gating. Matters because host-side scoring is how the metric is
  sanity-checked before trusting the leaderboard. Pre-existing,
  unrelated to v1.2.6 (surfaced in the 2026-08-14 Tier 3 pass);
  non-blocking for the tag.
- **D4 — the W1 stale-path failure surfaces as a nameless crash** — with
  a stale `TLC_COMPUTE_PLUGIN_VENV_KAGGLE_EXDARK` path the page shows
  only "Failed to load plugin: Internal Server Error" while the shop
  reports the new version · Ready · env built. The message names
  nothing — not the env var, not the expected path, not W1 — so it
  reads as a crash rather than a misconfiguration, and the tester has
  nothing to search the troubleshooting table for. This is the most
  likely first-contact failure for a Windows tester, and the 2026-08-14
  release walk confirmed the doc's own prediction of the W1 shape.
  Candidate fix: the plugin's load path checks whether its configured
  venv python exists and says so, with the path it looked for.
- **P2 — duration estimate ~40% low on multi-epoch runs** — predicted
  4m 21s against actuals of 6m 38s and 7m 15s on the two 2-epoch runs.
  Likely cause: the per-epoch median is calibrated on 1-epoch runs,
  which never carry the second epoch's collection pass. Pre-existing,
  unrelated to v1.2.6; record, don't fix now. (Distinct from the LIVE
  in-run ETA, which is measured per run and verified correct on the
  same runs.)

## Parked from the v1.2.8 release (2026-08-31) — v1.2.9 candidates

- **CC1 — Queue-panel `run_url` shape (adopt ctx.fail() rider's sibling;
  record-don't-fix, fails silently otherwise).** Finding: our train job
  emits `result()` with the run's raw local object URL (`C:/Users/...`);
  the 0.2.1 host consumes and serves it (confirmed live in the Queue API
  response), but the SaaS queue panel renders no Open-run link —
  plausibly it only links http(s) values. Investigated 2026-08-31: the
  SDK 0.3.x contract documents the argument as **"a run or a table
  URL"** (the tlc OBJECT URL — exactly what we send), the d.ts types it
  as a bare `run_url?: string`, and **no first-party plugin on 0.2.1 OR
  1.0.1 emits a result event at all** — we are the field's only user
  anywhere, so there is no reference emitter to imitate. Verdict:
  v1.2.9 should NOT switch to a dashboard http link on our own
  initiative: the worker cannot know the viewer's dashboard origin
  (dashboard_url is a browser-side config; a worker-baked absolute URL
  would be wrong by construction for remote-browse setups — the exact
  origin-pinning bug the fragment's root-relative links avoid), so the
  object URL is the only origin-neutral shape and matches the contract
  text verbatim. Action instead: ask the platform team what
  queue-panel.js expects from `run_url`; if it only links http(s),
  that's a frontend gap to file (the panel should resolve object URLs
  the way the rest of the Hub does). If the platform answer is "plugins
  must send an href," THEN v1.2.9 changes shape per their spec — with
  their mechanism for origin discovery, not a guess. Re-check after
  Paul's 0.3-contract host renders (or doesn't) the link post-tag.

## Parked from the v1.2.10 release (2026-09-03) — found while fixing the project root

All four surfaced in the sweep for "same shape as the v1.2.10 bug" (a
lookup or read whose failure is indistinguishable from a legitimate empty
value, absorbed by a plausible default). None is root-related; none rode
that release, per A3.

- **Remote project roots are not walkable.** `list_project_tables` derives
  the datasets dir from `_table_url` and then walks it with `pathlib`, so an
  `s3://` / `gs://` / `az://` `project-root-url` is mangled to `s3:/bucket/…`
  (verified) and the revision picker silently lists nothing. `tlc.Url` would
  handle the existence checks; the directory walk is the part with no remote
  equivalent. Nobody has asked for a remote root yet — the fix is a guard
  plus an honest "not supported for remote roots" reason on the picker, not
  a remote walker.
- **`kgUrlSeg` has no unknown-`kind` guard** (ui.html). `{project:…}[kind]`
  yields `undefined` for an unknown kind, and `String.match(undefined)` does
  NOT throw: it matches an empty regex, so the function returns `undefined`
  and the URL classifies as `drop`. All three callers pass literals today,
  so it is latent — but it is the same silent-miss shape as the bug
  v1.2.10 fixed, in the same function. Whoever adds a fourth caller owns it.
- **A corrupt `ui_config.json` is indistinguishable from a fresh install.**
  `config_store.load()` catches every exception and returns `{}`, so a
  truncated or half-written file silently reverts every field to the
  shipped defaults with nothing in the log. A one-line `_log.warning` in
  that handler would make it a report instead of a mystery.
- **Table lineage flattens on any string-form divergence — and it is
  ALREADY happening on real data.** `list_project_tables` matches parents by
  comparing `str(input_tables[i])` against `str(table.url)` keys; a
  separator, trailing-slash, or case difference makes every table a lineage
  root, and the `latest()` fallback then labels the mtime-newest table
  `latest: true`. Observed 2026-09-03 on `3lc-hub-next`'s own
  exdark-competition project (both the default root and a relocated copy,
  so it is not root-related and NOT a v1.2.10 regression):
  `table_revisions` on `exdark_train/tables/initial` returns
  `has_revisions: True` but `revisions: None` — the lineage walk from
  `latest` back to the base never arrives, so the force-reimport dialog
  cannot show a revision count and the picker's chain order falls back to
  mtime. Worth its own task: find whether the divergence is separator style
  or a genuinely different recorded input URL, then compare on `tlc.Url`
  identity rather than on strings.
